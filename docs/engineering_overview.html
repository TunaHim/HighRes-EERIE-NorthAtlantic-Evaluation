2. Why so much is streamed and so little is kept

The DKRZ server stores each day as one file for the whole globe. Whatever region you ask for, the whole globe comes over the internet. The pipeline cuts out the North Atlantic or north-west Europe box in memory, saves only that, and throws the rest away.

3. Problems the pipeline had to solve

decoding

Unreadable model files

IFS-FESOM2-SR data are raw GRIB messages that today's ecCodes library misreads. A small decoder removes one bookkeeping section first. Checked twice: an older library gives identical values, and a month of decoded daily data averages exactly to the model's own monthly file.

grids

Different grids

ERA5 uses rows of different length (a reduced Gaussian grid) and E-OBS a grid shifted by half a cell. Both are interpolated to the models' 0.25° grid so that maps can be subtracted point by point.

units and time

Different conventions

Rain came in kg m⁻² s⁻¹, m s⁻¹ and m per day; months were stamped at their end, middle or start. Everything is converted to mm/day, hPa and °C, and every month to its first day, with tests for each rule.

reliability

Slow and broken connections

Slow networks, sleeping laptops and server time-outs. One file per year, written atomically, so a failure costs one year; three retries; a restart continues where it stopped; everything logged.

safety

Network guard

A small guard (scripts/network_guard.ps1) watches the network every 5 seconds and stops all downloads if the machine joins any network other than the one allowed, so hundreds of gigabytes never go over a metered connection.

concurrency

Parallel reading crashed

The GRIB library crashed when several threads decoded at once. A lock around decoding fixed it, while downloads still run in parallel.

cost control

Measure before downloading

Every download was first tried on a few days, timed and sized, and the full cost estimated (hours, GB) before starting. That is how the 28 km ensemble was cut from 110 GB to about 16 GB.

honesty

Fair comparisons

Regional averages use exactly the same land cells for every dataset, so coastal cells that are partly sea in one dataset cannot bias the comparison.

5. Scaling up: what changes and what stays

The project runs on one laptop over an ordinary internet connection. The design is ready to grow: the yearly file is a natural unit of work, and the analysis does not care where the data came from. The main bottleneck today is the network.

To scale to…What it needsCode that changes
More members of the same modelsMore downloads; the analysis already handles a "member" dimension (used in notebooks 07 and 08).Add lines to the download plan only.

Less network traffic from a laptopAsk the server to cut the region before sending (server-side subsetting), instead of fetching whole-globe chunks.The open step in download.py.
Cloud storage and sharingSave as chunked Zarr instead of netCDF, so others can read the archive directly over the web.The save step in download.py.
Automatic checks on every changeRun the 66 tests on GitHub for every push (continuous integration).One configuration file.
An interactive dashboardRead the small Parquet tables already saved in app_assets/.A new app; no recomputation.

6. In one sentence

Public climate-model output from a remote data centre is discovered automatically, read without downloading whole files to disk, decoded, harmonised and cut to the region of interest year by year with retries and safeguards, stored as a small tested archive, and analysed by a library whose functions do not care which model, reanalysis or observation dataset they receive, which is what makes the same pipeline usable for more members, CMIP6 and CMIP7.
